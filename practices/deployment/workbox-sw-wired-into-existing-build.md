# Wire Workbox's generateSW into the existing build script; never auto-activate

## PATTERN
When adding a service worker to an app that already has a build pipeline, call
`workbox-build`'s `generateSW()` Node API from a small one-shot script chained
onto the END of the existing build command, rather than reaching for
`workbox-cli` as a separate step someone has to remember to run. The script
writes a fully-generated `sw.js` straight into the static-serving directory
(not a separate `dist/`), so every build regenerates it deterministically
from current file content -- there is nothing to remember to keep in sync.

Register the worker with `skipWaiting: false` and `clientsClaim: false`
(both Workbox defaults, but state them explicitly). This makes Workbox emit a
`message` listener (`postMessage({type:'SKIP_WAITING'})`) instead of an
unconditional `skipWaiting()` call, so a new worker sits WAITING until
something explicitly tells it to take over -- it never interrupts a page with
in-progress state (a live session, an open form, a game in progress) just
because a deploy happened in the background tab.

Scope `runtimeCaching` with function-based `urlPattern` matchers
(`({url}) => url.pathname.startsWith(...)`) rather than bare RegExp literals:
Workbox matches a RegExp `urlPattern` against the full `url.href`, not just
the pathname, so an unanchored-feeling pattern like `/^\/api\//` silently
never matches (the href starts with `https://...`, not `/`). A function
matcher avoids the footgun and reads more clearly at the call site.

Never precache or runtime-cache the app's data API routes. Precache/
runtime-cache only the app shell and static assets (JS/CSS/icons/manifest).

## WHY
- Piggybacking on the existing build command means the service worker can
  never silently drift out of date the way a manually-run generator can --
  there's no separate step to forget.
- Auto-`skipWaiting`/`clientsClaim` is the classic PWA footgun: a background
  deploy activates a new worker mid-session and the open tab's in-flight
  state (an active game, an unsaved form, a WebSocket room) gets pulled out
  from under it. Deferring activation to an explicit trigger (or the next
  cold load) costs nothing and avoids an entire class of "why did my session
  just reset" bug reports.
- `generateSW()` produces byte-identical output for identical input file
  content (confirmed by re-running the generator twice with no source
  changes), so gitignoring the output and always regenerating it at build
  time is safe -- it is genuine build output, not hand-authored or
  occasionally-refreshed vendored data.

## EXAMPLE
`package.json` build script (tcg's `dashboard/package.json`):
```json
"build": "pnpm run build:deps && tsc && node scripts/generate-sw.mjs"
```

`scripts/generate-sw.mjs` (trimmed):
```js
import { generateSW } from "workbox-build";

const isAppShellStatic = ({ url }) =>
  url.origin === self.location.origin && url.pathname.startsWith("/shared/");

await generateSW({
  globDirectory: PUBLIC_DIR,
  globPatterns: ["shell/shell.html", "shell/shell.js", /* ...explicit app-shell list */],
  swDest: SW_DEST,
  skipWaiting: false,   // message-based activation, not automatic
  clientsClaim: false,  // never take over an open tab mid-session
  cleanupOutdatedCaches: true,
  runtimeCaching: [
    { urlPattern: isAppShellStatic, handler: "StaleWhileRevalidate", options: { cacheName: "app-shell-static" } },
    // deliberately no entry matching /api/*
  ],
});
```

`.gitignore`:
```
# Generated service worker (Workbox generateSW, wired into the build script
# -- deterministic output, do not hand-edit or commit).
dashboard/src/public/sw.js
dashboard/src/public/sw.js.map
dashboard/src/public/workbox-*.js
dashboard/src/public/workbox-*.js.map
```

Client-side registration stashes the waiting worker instead of auto-reloading:
```js
navigator.serviceWorker.register("/sw.js").then((reg) => {
  reg.addEventListener("updatefound", () => {
    reg.installing?.addEventListener("statechange", () => {
      if (reg.installing.state === "installed" && navigator.serviceWorker.controller) {
        waitingWorker = reg.installing; // stashed; NOT auto-activated
      }
    });
  });
});
```

## CHECK
How to verify if a repo already follows this:
- [ ] The service worker is generated by a step chained onto the existing
      build command, not a separate manual/CI-only command.
- [ ] `skipWaiting`/`clientsClaim` are explicitly `false` (or the SW source
      shows a `message`-based `SKIP_WAITING` listener, not a bare call).
- [ ] `runtimeCaching` has no entry matching the app's own API routes.
- [ ] The generated SW file (and any Workbox runtime chunk) is gitignored,
      not committed.

## IMPLEMENT
1. Add `workbox-build` as a devDependency (not `workbox-cli`, so the config
   lives in versioned JS rather than a separate CLI-invoked JSON file).
2. Write a small `.mjs` script calling `generateSW()` with an explicit
   `globPatterns` allowlist (avoid a broad `**/*` glob that would sweep the
   whole app into the precache).
3. Chain the script onto the end of the existing build command.
4. Set `skipWaiting: false`, `clientsClaim: false` explicitly; wire client
   registration to stash (not auto-apply) a waiting worker.
5. Add the generated `sw.js` (+ `.map`) and any `workbox-*.js` runtime chunk
   to `.gitignore`.
6. Exclude API routes from every `runtimeCaching` entry.
